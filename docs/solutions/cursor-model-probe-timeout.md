# Cursor 模型列表探测误超时

## 现象与证据

2026-10-02，Raft 的「创建 Agent」窗口选择 Cursor CLI 后提示「无法从此 Computer 加载模型」。原截图没有终端报错，不能据此判断 Cursor API 不可达。

在 lyondeMacBook-Pro 上检查：

- PATH 中的 Cursor CLI 版本为 `2026.09.28-64d2043`，登录状态正常。
- `cursor-agent models` 能返回模型，输出符合现有解析规则。
- API 与官网的 TLS 校验及 HTTP 请求成功。系统代理和终端代理均未启用，但本机有 Clash TUN 网络链路。
- 使用现有探测参数连续执行 8 次，7 次成功，耗时 3.088～4.888 秒；另一次在约 5.091 秒返回 `ETIMEDOUT`，无模型输出。
- 已安装守护进程与源码均以同步 `spawnSync` 执行探测，期限 5 秒；服务端本地等待和跨副本转发等待也均为 5 秒。

本机实测说明，正常可用的 CLI 在网络波动下会超过探测期限，被误判为模型加载失败。同步等待还阻塞守护进程的事件循环；服务端与子进程共用同一个期限，缺少结果传输余量。没有取得原截图那次请求的服务端异常记录，因此不将推断当作该次请求的完整链路证据。

## 修复

- 使用异步 `execFile` 执行 Cursor 模型探测。
- Cursor 子进程期限改为 20 秒，服务端本地及转发等待统一为 25 秒，留出 5 秒结果传输余量。
- 两层期限从共享定义派生；其他运行时保留原来的等待期限。
- CLI 失败或超时仍返回可重试错误，不接受部分输出。现有连接世代校验和结果协议保持有效。

## 验证与边界

回归验证覆盖：6 秒才返回模型的真实子进程、等待期间事件循环响应、CLI 超时退出与部分输出拒绝、服务端迟到结果忽略、连接更换、等待定时器与监听器释放，以及跨副本等待期限。

源码中的新探测直接调用本机 CLI 成功返回 246 个模型，耗时约 4.061 秒，事件循环保持响应。

上线需要同时更新服务端和 Computer/守护进程：只更新一端仍受另一端旧期限约束。本次只提交源码与 PR，现用守护进程没有安装或重启；部署后需要重新验证「创建 Agent」窗口能加载模型。

本改动处理模型目录探测，不证明具体模型的推理调用或 Agent 创建已端到端通过。网络长期超过新期限时仍会返回可重试错误。
